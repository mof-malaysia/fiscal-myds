# FTDS Component Registry

This document describes the FTDS shadcn-compatible component registry structure and how to use it.

## Overview

FTDS is distributed as a **shadcn-compatible registry**: the shadcn CLI copies component source into your project instead of installing an npm package, so you own and can change the code.

## Registry Structure

The repository is the registry. The shadcn CLI reads it straight from GitHub ([shadcn docs](https://ui.shadcn.com/docs/registry/github)), and each release is also published as JSON on GitHub Pages.

```
registry.json                     # Root: includes the eight registries below
registry/
├── core/                         # Shared primitives, government chrome, utils, hooks
│   ├── registry.json
│   ├── components/ui/*.tsx
│   └── lib/ftds/{utils,hooks}/
├── app/                          # Service and officer tools
│   ├── registry.json
│   └── components/{ui,blocks}/*.tsx
├── marketing/                    # Agency and landing sites (components + registry:block)
│   ├── registry.json
│   └── components/{ui,blocks}/*.tsx
├── icons/                        # One item per icon, named icon-<name>
│   ├── registry.json
│   └── components/ui/icons/*.tsx
├── style/                        # ftds-init + colors, theme-light, theme-dark, theme-config, base-styles, variants-<name>
│   ├── registry.json
│   ├── styles/
│   └── components/ui/*.variants.ts
├── astro-core/                   # FTDS for Astro: core subset + astro-i18n, named astro-<name>
│   ├── registry.json
│   ├── components/ui/*.astro
│   └── lib/ftds/i18n/
├── astro-marketing/              # FTDS for Astro: marketing components and blocks
│   ├── registry.json
│   └── components/{ui,blocks}/*.astro
└── astro-icons/                  # One item per icon, named astro-icon-<name>
    ├── registry.json
    └── components/ui/icons/*.astro
```

The files under `registry/` are the installable copies: imports are already rewritten to the paths they install at. They are generated by `pnpm registry:build`, committed, and checked by CI. Don't edit them by hand.

Every item has one address, whatever its tier:

| Source       | Address                                                                                                          |
| ------------ | ---------------------------------------------------------------------------------------------------------------- |
| GitHub       | `mof-malaysia/ftds/<name>#<tag>`                                                                                 |
| GitHub Pages | `@ftds/<name>`, via `components.json`, served from `https://mof-malaysia.github.io/ftds/r/<version>/<name>.json` |

## Tiers

A component goes in the lowest tier that every consumer of it belongs to. App and Marketing items may depend on Core; App and Marketing never depend on each other (the generator fails the build if they do). Every tier installs flat into `components/ui/`, and every item shares one namespace, so names are unique across all registries (the build fails on a duplicate). That is why icons carry an `icon-` prefix: `icon-button` is the icon, `button` the component. Astro items carry an `astro-` prefix for the same reason. Blocks install into `components/blocks/`.

Classes a React and an Astro component share live in `packages/style/variants/<name>.ts`. Both import them as `@mof-malaysia/ftds-style/variants/<name>`; each file is its own item in the style registry, `variants-<name>`, installed as `components/ui/<name>.variants.ts`. The React and Astro items depend on it (so a project with both gets one copy), and the generators rewrite the import to match.

- **Core (40)**: alert-dialog, avatar, backlink, breadcrumb, button, callout, card, checkbox, cookie-banner, details, dialog, field, fieldset, footer, form, input, inset-text, label, link, masthead, menu, phase-banner, pill, popover, radio, scroll-area, select, separator, skeleton, skiplink, spinner, switch, tabs, tag, textarea, theme-switch, toast, toggle, toggle-group, tooltip. Plus `utils` and `hooks`.
- **App (34)**: app-shell, autocomplete, calendar, character-count, checkbox-group, combobox, command, context-menu, data-table, date-field, date-picker, daterange-picker, drawer, empty-state, error-summary, file-upload, menubar, meter, number-field, otp-field, page-header, pagination, panel, password-input, preview-card, progress, sheet, slider, stat, stepper, summary-list, table, task-list, toolbar.
- **Marketing (14)**: accordion, announce-bar, carousel, navbar, section-heading, site-footer, site-search; blocks cta-band, faq, feature-grid, hero, logo-cloud, stats-band, testimonial.
- **Astro core and Astro marketing**: FTDS for Astro, a selective subset of core plus marketing as native `.astro` components. It sits beside the React marketing tier and does not replace it; it never contains app components (the generator fails on any import it can't ship). See [docs/rfc/astro.md](./docs/rfc/astro.md).

## Migrating from 1.x

The flat `registry/ui` registry is gone. Re-add components from their tier's URL. Renamed or replaced:

| 1.x                                                                                   | 2.0                                                                               |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `ui/toggle` (Toggle + ToggleThumb)                                                    | `core/switch` (Switch, on Base UI Switch). `core/toggle` is now a pressed button. |
| `ui/dropdown` (Dropdown\*)                                                            | `core/menu` (Menu\*, with checkbox/radio items, groups, submenus)                 |
| `ui/input-otp` (InputOTP, InputOTPSlot; `input-otp` package)                          | `app/otp-field` (OTPField, OTPFieldSlot, OTPFieldSeparator; Base UI)              |
| `ui/footer` (multi-column: Footer, SiteInfo, SiteLinkGroup, ...)                      | `marketing/site-footer` (SiteFooter, SiteFooterInfo, SiteFooterLinkGroup, ...)    |
| —                                                                                     | `core/footer` is the plain mandatory government footer                            |
| `ui/accordion`, `ui/announce-bar`, `ui/navbar`                                        | `marketing/...`                                                                   |
| `ui/calendar`, `data-table`, `date-*`, `pagination`, `sheet`, `summary-list`, `table` | `app/...`                                                                         |
| everything else                                                                       | `core/...`                                                                        |

## How to Use

### Versions

The whole repository has one version. A release is a git tag (`v0.1.0`) and a folder on GitHub Pages (`r/v0.1.0/`), plus two moving channels: `r/v0/` (newest 0.x) and `r/latest/`. Within one install, every dependency comes from the same version. See [DEPLOYMENT.md](./DEPLOYMENT.md) for how releases are cut.

### For Users (Installing Components)

#### 1. Initialize shadcn in your project

```bash
npx shadcn@latest init
```

Keep the default Base UI component library: FTDS components are built on Base UI.

#### 2. Choose where to install from

**The `@ftds` namespace (recommended).** Add it to `components.json`, choosing a channel (`v0`, `latest`) or an exact version (`v0.1.0`):

```json
{
  "registries": {
    "@ftds": "https://mof-malaysia.github.io/ftds/r/v0/{name}.json"
  }
}
```

**Straight from GitHub.** Nothing to configure, but always pin a tag: without one you get unreleased work from `main`. The CLI reads each file through the GitHub API, which allows 60 unauthenticated requests an hour per IP address, so sign in with `gh auth login` or set `GH_TOKEN`.

#### 3. Install the FTDS styles

```bash
npx shadcn@latest add @ftds/ftds-init
# or: npx shadcn@latest add mof-malaysia/ftds/ftds-init#v0.1.0
```

#### 4. Import FTDS styles in your global CSS

```css
@import url("https://fonts.googleapis.com/css2?family=Inter:ital,opsz,wght@0,14..32,100..900;1,14..32,100..900&display=swap");
@import "tailwindcss";
@import "tw-animate-css";
@import "../styles/ftds.css";
```

#### 5. Add components to your project

```bash
npx shadcn@latest add @ftds/button --overwrite
# or: npx shadcn@latest add mof-malaysia/ftds/button#v0.1.0 --overwrite
```

This will:

- Copy the component source code to your project
- Install npm dependencies (`@base-ui/react`, etc.), pinned to the ranges FTDS is built against
- Install registry dependencies (utils, hooks, icons, other components) from the same version

#### 6. Use the component

```tsx
import { Button } from "@/components/ui/button";

export function MyComponent() {
  return (
    <Button variant="primary-fill" size="medium">
      Click me
    </Button>
  );
}
```

### Component Dependencies

Components have two types of dependencies:

#### npm Dependencies

External packages that will be installed via npm/pnpm/yarn:

- `@base-ui/react` - Primitive components
- `class-variance-authority` - Variant management
- `tailwind-merge` - Tailwind class merging
- `react-day-picker` - Date picker
- `@tanstack/react-table` - Data table (v8)
- `cmdk` - Command palette
- `date-fns` - Date formatting

#### Registry Dependencies

Other FTDS items, referenced by their full address (`mof-malaysia/ftds/utils` in the repository, a URL in the Pages JSON):

- `utils` - Utility functions (clx)
- `hooks` - Custom React hooks
- Icons and other components (e.g., button, menu), possibly from the core registry

The shadcn CLI automatically installs all dependencies when you add a component.

## For Maintainers (Building the Registry)

### Prerequisites

- Node.js 18+
- pnpm 9+
- tsx (installed as dev dependency)

### Build Commands

```bash
# Build registry.json and registry/ (all generators)
pnpm registry:build

# Check it with shadcn registry validate
pnpm registry:validate

# Clean registry files
pnpm registry:clean
```

### Build Process

`pnpm registry:build` runs `scripts/registry/build-multi.ts`, which runs the generators, checks every item name is unique and writes the root `registry.json`. Each generator writes its registry as files plus a `registry.json` (`writeRegistry` in `scripts/registry/utils.ts`):

- `generate-components.ts` reads `packages/react/src/components/{core,app,marketing}`, `hooks` and `utils`, and writes one registry per tier (`utils` and `hooks` ship from core):
  - Rewrites relative imports to the paths files are installed at:
    - `"../../utils"` → `"@/lib/ftds/utils"`, `"../../hooks"` → `"@/lib/ftds/hooks"`
    - `"../../icons/chevron-down"` → `"@/components/ui/icons/chevron-down"` (barrel `"../../icons"` imports are split per icon)
    - `"./button"` and `"../core/button"` → `"@/components/ui/button"`
  - Turns those imports into `registryDependencies` as item addresses (`mof-malaysia/ftds/button`).
  - Pins npm `dependencies` to the ranges in `packages/react/package.json`.
  - Emits app and marketing files that start with a `// registry:block` comment as `registry:block`.
  - Fails if an app item depends on marketing or vice versa.
- `generate-icons.ts` writes one item per file in `packages/react/src/icons`, named `icon-<file>`. Those files are generated from `packages/react/src/svg/icons/*.svg` by `pnpm icons:generate`; run it first when the SVGs change.
- `generate-style.ts` reads `packages/style/styles` and writes `ftds-init` (combined `styles/ftds.css`) plus the granular style items (`styles/ftds/<name>.css`).

After adding, moving or renaming a component file, run `pnpm components:sync-exports` so `packages/react/package.json` exports match the tiers.

Dependencies are unpinned on `main`. The Release workflow builds with `FTDS_REF=v0.1.0`, which appends `#v0.1.0` to every dependency, and tags that build; never commit a pinned build to `main` (CI fails, since it rebuilds without `FTDS_REF`).

`scripts/registry/build-json.ts` converts a registry source (this checkout or a release tag) into the JSON published on GitHub Pages: one `<name>.json` per item with the file contents inlined, and dependencies rewritten to URLs in the same folder. `pnpm deploy:prepare` runs it for every release tag.

### Registry File Format

Each `registry/<name>/registry.json` follows shadcn's [registry schema](https://ui.shadcn.com/schema/registry.json). File paths are relative to that `registry.json`; the CLI installs each file by the alias folder in its path (`ui`, `lib`), so `components/ui/button.tsx` lands in your ui folder.

```json
{
  "name": "button",
  "type": "registry:ui",
  "dependencies": ["@base-ui/react@^1.9.0", "class-variance-authority@^0.7.1"],
  "registryDependencies": ["mof-malaysia/ftds/utils"],
  "files": [{ "path": "components/ui/button.tsx", "type": "registry:ui" }]
}
```

The Pages JSON for the same item is a [registry-item](https://ui.shadcn.com/schema/registry-item.json) with `content` inlined and `registryDependencies` as URLs (`https://mof-malaysia.github.io/ftds/r/v0/utils.json`).

### Item Types

- `registry:ui` - Components and icons
- `registry:block` - Marketing page sections (installed to `components/blocks/`)
- `registry:lib` - `utils` and `hooks` (installed under `lib/ftds/`)
- `registry:file` - Styles, with an explicit `target` (`~/styles/...`)

## Testing Locally

### 1. Build a JSON registry against a local server

```bash
pnpm registry:build
pnpm tsx scripts/registry/build-json.ts . deploy/r/dev http://localhost:8765/r/dev
npx serve deploy -l 8765
```

### 2. Create a test project

```bash
npx shadcn@latest init -t next -n test-ftds-registry
cd test-ftds-registry
```

### 3. Install FTDS styles and components

Add `"registries": { "@ftds": "http://localhost:8765/r/dev/{name}.json" }` to `components.json`, then:

```bash
npx shadcn@latest add @ftds/ftds-init
npx shadcn@latest add @ftds/button --overwrite
```

To test the GitHub route, push a branch and install from it: `npx shadcn@latest add mof-malaysia/ftds/button#<branch>` (dependencies on an unpinned branch build come from `main`).

### 4. Import styles in `app/globals.css`

```css
@import "tailwindcss";
@import "tw-animate-css";
@import "../styles/ftds.css";
```

### 5. Test the component

Create a test page and verify:

- Component files are copied correctly
- Dependencies are installed
- Imports resolve properly (`npx tsc --noEmit`)
- Styles apply correctly (`npx next build`)
- Component renders and functions as expected

## Dependency Graph

Some components depend on other components from the registry:

```
button → utils
accordion → utils, icons
navbar → button, link, icons, utils
toast → hooks, icons, utils
hooks → toast
alert-dialog → dialog, icons, utils
data-table → table, button, checkbox, icons, utils
```

The shadcn CLI automatically resolves and installs these dependencies.

## Troubleshooting

### Component not found

If you get "was not found" errors:

1. Check the name in [`registry.json`](./registry.json) and the files it includes. Icons are `icon-<name>`.
2. For `@ftds/...`, check the `components.json` URL ends in `/{name}.json` and its version folder exists (`https://mof-malaysia.github.io/ftds/r/versions.json`).
3. For `mof-malaysia/ftds/...`, check the tag exists. 1.x `registry/ui` URLs no longer exist; see [Migrating from 1.x](#migrating-from-1x).

### Import errors

If imports don't resolve:

1. Check that aliases are configured in `components.json` (`npx shadcn@latest init` sets them up)
2. Verify `tsconfig.json` maps `@/*` to your source root

### Type errors mentioning `render` or `asChild`

FTDS is built on Base UI. Make sure `components.json` uses a Base UI style (e.g. `base-nova`), i.e. `npx shadcn@latest init` with the default `base` library, not `--base radix`.

### Missing styles

If components don't look correct:

1. Ensure `styles/ftds.css` exists (`ftds-init` was added)
2. Verify it is imported after `@import "tailwindcss";` and `@import "tw-animate-css";` in your global CSS

### Dependency issues

If npm dependencies aren't installing:

1. Check your package manager (npm/pnpm/yarn)
2. Clear cache and reinstall: `rm -rf node_modules && pnpm install`
3. Verify internet connection for package registry
